# How Linux Schedules Tasks: CFS, EEVDF, and What It Means for PostgreSQL Active Connections per Core

## TL;DR
- Linux's fair-class scheduler is a weighted-fair, virtual-time scheduler: **CFS** (2007–2023) picked the runnable task with the smallest `vruntime` from a red-black tree; **EEVDF** (merged in kernel 6.6, October 2023) replaced the *selection* logic with "earliest virtual deadline among eligible tasks," keeping the same `vruntime`/weight machinery but adding lag-based eligibility and per-task time slices. In both, once runnable tasks exceed ~8 per core the per-task slice shrinks toward the floor (~0.75 ms) and per-task scheduling latency grows roughly linearly with the number of runnable tasks.
- On one core, only one task runs at a time. With the default base slice of 0.75 ms and a ~6 ms target latency, about **8 equal-priority runnable tasks** fit in one scheduling period before the period stretches to `nr_running × base_slice`; beyond that, each additional runnable task adds ~0.75 ms of wait to everyone else's round-trip and each context switch costs ~1–10 µs of direct overhead plus larger indirect cache/TLB costs.
- For PostgreSQL — where every connection is a full OS backend process — the scheduler math is why the community formula **`connections ≈ (core_count × 2) + effective_spindle_count`** works: **effective active (runnable) backends per core should be ≈ 1–3, not dozens.** Idle connections are cheap to *schedule* (they aren't runnable) but expensive in memory (~2–10 MB each) and in PostgreSQL-internal overhead (e.g., `GetSnapshotData()`); active backends beyond ~2× cores cause timeslice dilution, linearly growing query latency, context-switch and cache thrashing, and LWLock-contention amplification. Size PgBouncer's `default_pool_size` to roughly `(cores × 2)` per pool, not to client count.

## Key Findings

1. **CFS and EEVDF share a virtual-time core.** Both scale each task's runtime by `NICE_0_LOAD/weight` to produce `vruntime`, keep runnable tasks in an `rb_root_cached` red-black tree keyed on virtual time (O(log n) insert/delete, O(1) leftmost access), and track `min_vruntime`/`avg_vruntime` to place waking tasks fairly. EEVDF is best understood as an evolution *inside* `fair_sched_class`, not a rewrite of the fairness model.

2. **The tunables changed materially at 6.6.** CFS exposed `sched_latency_ns` (~6 ms base, scaled by CPU count), `sched_min_granularity_ns` (0.75 ms base), `sched_wakeup_granularity_ns` (1 ms), and `sched_nr_latency` (8). EEVDF collapsed these into a single primary knob, `sched_base_slice_ns` (default 750,000 ns = 0.75 ms), and removed the wakeup-granularity heuristic; the period-stretch behavior is now expressed through per-task slices and deadlines rather than an explicit latency target.

3. **Scheduling decisions happen at three points**: the periodic tick (`CONFIG_HZ`, typically 250 Hz = every 4 ms on servers; 1000 Hz = 1 ms on many desktops), wakeups (a newly runnable task may preempt), and voluntary sleeps/yields. High-resolution timers can also drive preemption between ticks for slice enforcement.

4. **Per-core capacity is bounded by virtual time, not by a hard task cap.** The rbtree scales to thousands of runnable tasks at O(log n), so nothing "breaks," but each runnable task's share is `1/nr_running` of the CPU and its worst-case wait for the CPU grows about linearly with `nr_running × base_slice`. Context-switch direct cost is ~1–10 µs; indirect cache/TLB cost can be far larger.

5. **PostgreSQL's process-per-connection model maps directly onto this.** A runnable backend = a runnable task on the runqueue. On an N-core box, at most N queries execute simultaneously; every additional *active* backend is waiting (run queue, lock, or I/O). The measured penalty of overcommitting connections is severe and well-documented.

## Details

### 1. CFS internals

**Virtual runtime and the red-black tree.** CFS ("Completely Fair Scheduler," Ingo Molnar, merged in Linux 2.6.23, 2007) models an "ideal, precise multi-tasking CPU" where N equal-priority tasks each run at 1/N speed. Since real hardware runs one task per core at a time, CFS tracks **virtual runtime** (`vruntime`, a field in `struct sched_entity` in `include/linux/sched.h`). On each accounting update (`update_curr()` in `kernel/sched/fair.c`), the task's actual elapsed time `delta_exec` is added to `sum_exec_runtime`, and a weight-scaled amount is added to `vruntime` via `calc_delta_fair()`:

```
vruntime += delta_exec × (NICE_0_LOAD / se->load.weight)
```

`calc_delta_fair()` calls `__calc_delta()` only when the weight differs from `NICE_0_LOAD` (1024). A high-weight (low-nice) task advances `vruntime` slowly and thus accrues more real CPU; a low-weight task advances quickly. Runnable tasks live in a time-ordered red-black tree (`cfs_rq->tasks_timeline`, an `rb_root_cached` that caches the leftmost node for O(1) access to the smallest-`vruntime` task). CFS "picks the leftmost task." Insert/remove are O(log n).

**min_vruntime.** `cfs_rq->min_vruntime` is a monotonically increasing floor tracking the smallest `vruntime` in the queue; it is used to place newly-woken or newly-created entities so they neither get an unfair burst nor are starved. On wakeup CFS historically placed the task at roughly `min_vruntime − sched_latency/2` (with `GENTLE_FAIR_SLEEPERS`) so it runs soon without monopolizing.

**Targeted latency, minimum granularity, and period stretch.** The classic CFS knobs (Documentation and `kernel/sched/fair.c`):
- `sysctl_sched_latency` — targeted preemption latency ("scheduling period"); default **6 ms**, scaled `× (1 + ilog(ncpus))`, so on a multi-core box it reads ~ up to 24 ms (older kernels documented 20 ms). This is the window in which every runnable task should run once.
- `sysctl_sched_min_granularity` — floor on a task's slice; default **0.75 ms** (`750000` ns), also CPU-scaled. Some distributions shipped 3–4 ms.
- `sched_nr_latency = 8` — kept at `sched_latency / min_granularity`; the threshold number of runnable tasks past which the period stretches.
- `sysctl_sched_wakeup_granularity` — default **1 ms**; a waking task must beat the current task's `vruntime` by this much to force wakeup preemption.

When `nr_running ≤ sched_nr_latency` (≤ 8), each task's slice ≈ `sched_latency × weight/total_weight`. When `nr_running > 8`, the period is recomputed as `__sched_period() = nr_running × min_granularity` so no task drops below the granularity floor — meaning **the effective latency now grows linearly with the number of runnable tasks.** As the SUSE/openSUSE tuning docs state: "When the number of runnable tasks exceeds `sched_latency_ns/sched_min_granularity_ns`, the slice becomes `number_of_running_tasks × sched_min_granularity_ns`."

**Timeslice computation and the tick.** `sched_slice()` computes a task's wall-clock slice from the period, proportional to weight: `s = period × (se_weight / cfs_rq_weight)`. The periodic tick (`scheduler_tick()` in `kernel/sched/core.c` → `task_tick_fair()` → `entity_tick()` → `check_preempt_tick()`) fires at `CONFIG_HZ`: common values are 100, 250, 300, and 1000 Hz; **250 Hz (4 ms) is the typical server default**, 1000 Hz (1 ms) is common on desktops. `check_preempt_tick()` computes the ideal slice, and if the current task has run longer than that slice (or longer than `min_granularity`), sets the reschedule flag; it also preempts if the `vruntime` gap to the leftmost task exceeds the ideal slice.

**Nice, weights, PELT.** Nice values (−20…+19) map to weights through `sched_prio_to_weight[40]` in `kernel/sched/core.c`, with nice 0 = 1024 and each nice step ≈ a 1.25× weight change ("~10% CPU per nice level"): −20 → 88761, −5 → 3121, 0 → 1024, +5 → 335, +19 → 15. So nice −20 vs +19 is ~88761/15 ≈ 5917× CPU ratio. **PELT (Per-Entity Load Tracking)** decomposes each entity's history into ~1 ms (1024 µs) periods weighted by a geometric series with `y^32 = 0.5` (32 ms half-life), maintaining `load_avg`/`util_avg` in `struct sched_avg`; these signals feed load balancing and (with schedutil) frequency selection, not the local pick decision.

**Wakeup preemption & groups.** `check_preempt_wakeup` decided whether a waking task preempts the running one, gated by wakeup granularity. `CONFIG_FAIR_GROUP_SCHED` + cgroups allow hierarchical fair sharing (`cpu.shares` in v1, `cpu.weight` 1–10000 default 100 in v2, mapped through the same weight table); autogroups apply the same mechanism per-session for desktop interactivity. CFS bandwidth control (`cpu.max`, quota/period) can throttle a group even when CPUs are idle.

### 2. EEVDF internals

**Why EEVDF.** CFS's fairness gave every task its share but no way to express *latency* needs without abusing nice or realtime classes, and it accreted fragile heuristics. Peter Zijlstra (Intel) posted the "Earliest Eligible Virtual Deadline First" implementation in March 2023, based on the 1995 paper "Earliest Eligible Virtual Deadline First: A Flexible and Accurate Mechanism for Proportional Share Resource Allocation" by Ion Stoica and Hussein Abdel-Wahab. It was merged as an option in **6.6 (October 2023)**; commit `147f3efaa241` ("sched/fair: Implement an EEVDF-like scheduling algorithm") implemented it and `5e963f2bd465` ("sched/fair: Commit to EEVDF") made it unconditional. Zijlstra: "EEVDF is a better defined scheduling policy, as a result it has less heuristics/tunables. There is no compelling reason to keep CFS around."

**Eligibility and lag.** EEVDF assigns each task a fair share and tracks **lag** = (share it should have received) − (actual received time). A task is **eligible** iff `lag ≥ 0` (its `vruntime` is at or behind the weighted-average `vruntime`, `avg_vruntime`). The kernel's `vruntime_eligible()` compares `vruntime × load` against the accumulated `avg_vruntime`. A key invariant, noted in LWN's worked three-task example, is that the sum of all lag values in the system is always zero. Ineligible (negative-lag) tasks wait until virtual time advances enough to make them eligible again; corbet (LWN) notes that if a runqueue would otherwise go idle, virtual time is skipped forward to the nearest eligible time so the CPU never idles with work pending.

**Virtual deadline and selection.** Each task gets a requested slice (`se->slice`, stored alongside `vruntime` and `vlag` in `struct sched_entity`) and a **virtual deadline** `vd = ve + slice/weight`, computed in `kernel/sched/fair.c` as `se->deadline = se->vruntime + calc_delta_fair(se->slice, se)`. EEVDF runs **the eligible task with the earliest virtual deadline** (`pick_eevdf()` walks the augmented rbtree, pruning subtrees by eligibility). Because a shorter requested slice yields an earlier deadline, latency-sensitive tasks that ask for small slices are naturally scheduled first — without heuristics.

**base_slice_ns and removed knobs.** EEVDF's single primary tunable is `sysctl_sched_base_slice` (`/sys/kernel/debug/sched/base_slice_ns` or `sched_base_slice_ns`), default **750000 ns (0.75 ms)**, defined in `kernel/sched/fair.c` as `unsigned int sysctl_sched_base_slice = 750000ULL;` (with `normalized_sysctl_sched_base_slice = 750000ULL`). Commit `e4ec3318a17f` ("sched/debug: Rename sysctl_sched_min_granularity to sysctl_sched_base_slice") renamed the old `sysctl_sched_min_granularity` to `sysctl_sched_base_slice`. `sched_latency_ns` and `sched_wakeup_granularity_ns` are gone as scheduling drivers (the old CFS sysctls having moved to debugfs in 5.13). Note the kernel documentation caveat: "In case CONFIG_HZ results in base_slice_ns < TICK_NSEC, the value of base_slice_ns will have little to no impact on the workloads" — i.e., at 250 Hz (4 ms tick) a 0.75 ms base slice can't be enforced between ticks without hrtimer-driven preemption.

**Lag across sleep/wakeup; PLACE_LAG, RUN_TO_PARITY.** Feature flags live in `kernel/sched/features.h`:
- `PLACE_LAG` (default true): on wakeup, place the task using its preserved lag (`se->vlag`) so it neither starves nor bursts (EEVDF placement strategy #1).
- `PLACE_DEADLINE_INITIAL` (true): "Give new tasks half a slice to ease into the competition."
- `RUN_TO_PARITY` (true at merge): "Inhibit (wakeup) preemption until the current task has either matched the 0-lag point or until it has exhausted its slice." Added by commit `63304558ba5d` ("sched/eevdf: Curb wakeup-preemption") after Mike Galbraith and others found EEVDF over-scheduled. In a test on a 3rd-Gen AMD EPYC (2×64C/128T, NPS1) by K Prateek Nayak, enabling RUN_TO_PARITY cut context switches on `perf bench sched messaging -g 20 -t -l 5000` from **3,723,554** (NO_RUN_TO_PARITY) to **2,556,535**. Disabling it lowers max latency but hurts throughput.

Lag is preserved when a task sleeps and restored on wake, so a task that overran its share pays it back later. **Delayed dequeue** (commit `152e11f6df29`, "sched/fair: Implement delayed dequeue," merged for **6.12**) keeps an ineligible sleeping task on the runqueue marked "deferred dequeue," letting its negative lag decay over *virtual* time (competition) rather than wall time; positive lag is retained indefinitely. This prevents gaming the system by micro-sleeping at the end of a slice.

**Custom slice support (6.12).** The "Complete EEVDF" series (LWN, April 2024) added the ability for any task to request a slice via `sched_setattr()` using the `sched_attr::sched_runtime` field, allowed range **100 µs to 100 ms**, plus allowing a shorter-slice task to wakeup-preempt a longer-slice one (`PREEMPT_SHORT`). This is the latency-nice concept realized: the same total CPU is delivered in more or fewer, shorter or longer slices.

**Latency vs throughput, regressions.** EEVDF generally improves p99 latency and consistency (LWN quoting Zijlstra: EEVDF "schedules a lot more consistently than CFS and has a bunch of latency wins"). Reported deltas during the 6.6–6.8 cycle were rough throughput parity with CFS on kernbench-style workloads and meaningful p99 improvements on schbench/hackbench at moderate overcommit. But there were real regressions: the eligibility check itself regressed some workloads (one LKML data point: CFS 168 ms vs EEVDF-with-eligibility 206 ms vs EEVDF-without 143 ms); vhost/kworker wakeup patterns that relied on CFS's wakeup boost regressed (prompting `NOLAG_WAKEUP`/delayed-dequeue work by Tobias Huschle and others); and a scheduler performance regression since v6.11 was bisected to a DELAY_DEQUEUE-related commit (`729288bc6856`, "kernel/sched: Fix util_est accounting for DELAY_DEQUEUE"). As of 2025–2026, refinements continue — Vincent Guittot's "Manage lag and run to parity with different slices" series, and OSPM 2026 discussions where a short-slice cyclictest task could still see ~9 ms max latency under hackbench overload, with any task needing more than the 0.75 ms base slice preempted before finishing.

### 3. Quantitative analysis

**How often decisions happen.** Preemption checks occur at every tick (250 Hz → every 4 ms on typical servers; 1000 Hz → 1 ms), at every wakeup, and at every voluntary yield/sleep. With hrtimer-driven slice enforcement the effective granularity approaches `base_slice_ns` (0.75 ms) when HZ permits. On a busy runqueue, a CPU-bound workload therefore context-switches on the order of hundreds to low-thousands of times per second per core.

**Tasks per period on one core.** With CFS defaults (~6 ms base latency, 0.75 ms min granularity) the ratio is exactly `sched_nr_latency = 8`: up to **8 equal-priority runnable tasks** each get ~0.75 ms within one ~6 ms period. Under EEVDF the same arithmetic holds through the base slice: with 8 runnable tasks each gets one 0.75 ms slice per ~6 ms round. Beyond 8, the round lengthens to `nr_running × 0.75 ms`:
- 10 runnable tasks → ~7.5 ms round; each task waits ~6.75 ms between slices.
- 50 runnable tasks → ~37.5 ms round; ~36.75 ms wait.
- 100 runnable tasks → ~75 ms round; ~74 ms wait.
- 1000 runnable tasks → ~750 ms round; ~0.75 s worst-case wait for the CPU.

So **per-task scheduling latency grows about linearly with the number of runnable tasks**, while the per-task CPU *share* falls as `1/nr_running`. The slice cannot shrink below the granularity floor, which is what forces the period (and hence latency) to stretch.

**Context-switch cost.** Direct cost (save/restore registers, run the scheduler, switch page tables/TLB) is commonly cited at **~1–10 µs**; Eli Bendersky's lmbench-style microbenchmark ("Measuring context switching and memory overheads for Linux threads," 2018) measured "between 1.2 and 1.5 microseconds per context switch, accounting only for the direct cost, and pinning to a single core… Without pinning, the switch time goes up to ~2.2 microseconds." Indirect cost — cold L1/L2/L3 and TLB after the switch — often dominates and can reach tens to hundreds of microseconds-equivalent for large working sets (research pegs net cost at "thousands of cycles, or tens to hundreds of microseconds"). PCID/ASID (x86 kernels ≥ 4.14) avoids full TLB flushes on switch, reducing the direct penalty. The practical implication: if slices shrink toward 0.75 ms and switching costs a few µs plus cache refill, the *overhead fraction* stays small for CPU-bound work but the *cache pollution* from many competing working sets degrades throughput well before the raw switch cost matters.

**Behavior with tens/hundreds/thousands of runnable tasks.** rbtree operations remain O(log n) — log2(1000) ≈ 10 comparisons — so the scheduler itself is not the bottleneck. The degradation is: (a) latency per task grows ~linearly; (b) each task's cache footprint is repeatedly evicted by the others (cache thrashing); (c) more involuntary context switches; (d) for lock-holding tasks, being descheduled mid-critical-section stalls every waiter (the convoy / lock-holder-preemption effect).

### 4. How many ACTIVE PostgreSQL connections per core?

**Idle vs active.** PostgreSQL uses one OS backend process per connection. An **idle** connection is *not runnable* — it sits in a blocking `recv()` and imposes **no scheduling cost** (it's off the runqueue). Its costs are memory (~2–10 MB resident per backend depending on version/workload; AWS measured 1.5–14.5 MB across query patterns) and PostgreSQL-internal overhead — most importantly `GetSnapshotData()`, whose cost scales with the number of connections regardless of activity. An **active** backend (state `active`, actually executing a query on-CPU or waiting to be) *is* a runnable task and is what the scheduler math above governs.

**The classic guidance.** The PostgreSQL wiki ("Number Of Database Connections") gives the durable rule: "A formula which has held up pretty well across a lot of benchmarks for years is that for optimal throughput the number of active connections should be somewhere near **`((core_count * 2) + effective_spindle_count)`**. Core count should not include HT threads, even if hyperthreading is enabled." Effective spindle count ≈ 0 when the working set is fully cached, approaching the number of independent disks as cache-hit rate falls; on NVMe/SSD with a hot working set it's ~0–1. So a 4-core, SSD box → `(4×2)+1 = 9` active connections. HikariCP's Brett Wooldridge distills it verbatim: "You want a small pool, saturated with threads waiting for connections" (worked example: "9 = ((4 * 2) + 1)"). This maps directly to the scheduler: **only `core_count` queries can run at any instant; the `×2` assumes that while one backend waits on I/O another can use the core; the spindle term adds concurrency for real parallel I/O.** In other words, target **~1–3 runnable backends per core** (≈1 for pure CPU-bound, ~2–4 with I/O wait), which keeps each core's runqueue at or below the ~8-task point where CFS/EEVDF latency starts stretching.

**What happens as active backends per core grow.** This is the scheduler math applied to queries:
- **Timeslice dilution / linear latency growth.** With k runnable backends on one core, each query gets ~`1/k` of the core and waits ~`(k−1)×base_slice` between slices. A CPU-bound query that needs 10 ms of CPU finishes in ~10 ms if it has the core to itself, but takes ~`10 ms × k` of wall-clock when sharing with k−1 equally-busy peers, plus scheduling waits. So **query latency grows roughly linearly with the number of active backends per core** once you exceed core count.
- **Context-switch and cache thrashing.** Each backend has its own working set (catalog caches, buffers being scanned); piling many onto a core evicts each other's cache lines, so effective throughput per core drops beyond the raw switch cost.
- **LWLock contention amplified by descheduling.** PostgreSQL's LWLocks (buffer mapping, lock manager, WAL insert) are hybrid spin-then-sleep primitives. If a backend holding an LWLock is descheduled (because the core is overcommitted), every waiter stalls until it is rescheduled — a lock-holder-preemption convoy. This gets dramatically worse when active connections exceed vCPUs. The AWS Database Blog ("Improve PostgreSQL performance: Diagnose and mitigate lock manager contention," Aurora PostgreSQL 16.6 on db.r7g.4xlarge, 16 vCPU) documents that once each backend's fast-path lock capacity (16 slots, `FP_LOCK_SLOTS_PER_BACKEND = 16`) is exceeded, the shared lock table's LWLocks serialize and "throughput can drop significantly—our tests in this post show up to a 34 percent performance difference" (their partition-pruning fix moved throughput from ~46,000 to ~59,000 tps). AWS's wait-event guidance adds: "Typically, when this concurrency is higher than the number of vCPUs, the LWLock:lock_manager wait event appears."

**Concrete numeric scenarios (single core, EEVDF/CFS defaults, base slice 0.75 ms).** Consider one core with purely CPU-bound backends:
- **10 active backends:** round ≈ `10 × 0.75 = 7.5 ms`; each backend sees ~6.75 ms of scheduling wait per slice and ~1/10 of the core. A 5 ms-CPU query completes in ≈50 ms wall-clock.
- **50 active backends:** round ≈ 37.5 ms; ~36.75 ms wait per turn; ~1/50 of the core; the same 5 ms query takes ≈250 ms.
- **100 active backends:** round ≈ 75 ms; ~74 ms wait; ~1/100 of the core; ≈500 ms for that query — plus disproportionately worse real-world degradation once LWLock contention and cache thrashing compound.

These are optimistic lower bounds (pure CPU, no lock contention). Real PostgreSQL measurements show the compounding. Andres Freund's connection-scalability study ("Analyzing the Limits of Connection Scalability in Postgres," Azure/Citus, Oct 2020; single 20-core/40-thread box, PostgreSQL 12, read-only pgbench) found that even *idle* connections drag throughput: a single active connection fell from **33,457 TPS with 0 idle connections to 14,496 TPS with 10,000 idle** (a ~57% loss), with the CPU profile bottleneck "entirely in the GetSnapshotData() function." Freund's conclusion: "the fact that a single active connection slows down by more than 2x due to concurrent idle connections points to a very clear issue." Non-idle overcommit is worse. The `(core×2)` formula exists precisely because throughput climbs to a peak near ~2× cores and then falls off past the "knee," as the PostgreSQL wiki describes: "you will see performance climb as connections rise until you hit saturation, and then you have a 'knee' after which performance falls off… the issue is intrinsic."

**PgBouncer sizing from the scheduler math.** Because effective parallelism is ~`core_count`, the pool that talks to Postgres should be sized to the *database's* parallelism, not client count:
- Set PgBouncer `default_pool_size` ≈ `(cores × 2) + effective_spindles` **per (user,database) pool** — e.g., ~9 for a 4-core SSD instance, ~17 for 8-core. Multiple pools must satisfy `Σ(pools × default_pool_size) < max_connections − reserved`.
- Use **transaction mode** for maximum multiplexing (a backend is held only for the duration of a transaction, released on COMMIT/ROLLBACK), which lets thousands of client connections share a small backend pool; use **session mode** only where session state (LISTEN/NOTIFY, session advisory locks, server-side prepared statements) is required.
- `max_client_conn` can be large (thousands) — PgBouncer holds each client cheaply (its docs cite ~2 KB per client) — but `default_pool_size`/`max_db_connections` must stay small. Heroku's operational rule of reserving ~25% of `max_connections` for admin/direct connections (pooler ≤ 75%) is a sane default.
- Keep total *active* backends across all app instances and pods under the `(cores × 2)` envelope — the common failure mode is N pods each with a large local pool silently multiplying into thousands of backends.

## Recommendations

1. **Default to the formula, then measure.** Start PgBouncer `default_pool_size` at `(physical_cores × 2) + effective_spindle_count` per pool (spindles ≈ 0–1 for cached/NVMe). For a 4-core SSD instance that's ~9; for 16 cores ~33. This keeps each core's runnable-backend count near or below the ~8-task point where CFS/EEVDF latency begins stretching linearly. Benchmark with your workload and adjust in small steps.
2. **Watch the right signals to move the number.** Increase the pool only if CPU is underutilized *and* PgBouncer `cl_waiting > 0`/`maxwait` is rising (clients starved for backends). Decrease it if CPU is pinned, query p99 latency climbs, or you see `LWLock:lock_manager`/`LWLock:LockManager`, `BufferMapping`, or high involuntary context switches (`pidstat -w`, `perf sched latency`). The threshold that should change your decision: **active backends per core > ~2–4** with rising lock-manager waits is the signal to shrink the pool or add cores, not raise `max_connections`.
3. **Prefer transaction-mode pooling** for stateless/high-concurrency apps; reserve session mode for connections needing session features. Disable server-side prepared statements in the driver when using transaction mode (or use a pooler that tracks them).
4. **Keep idle connections down independently.** Even idle backends cost memory and `GetSnapshotData()` overhead (Freund's ~2× single-connection slowdown from 10,000 idle peers); set `idle_in_transaction_session_timeout` and `idle_session_timeout`, and let the pooler concentrate work onto few backends rather than raising `max_connections`.
5. **Don't fight the scheduler with nice/realtime.** For a database, leave backends at nice 0. If you must protect latency-critical backends, EEVDF's `sched_setattr()` custom-slice (6.12+) is the principled lever, but pooling and query optimization dominate. Only isolate cores (`isolcpus`/`nohz_full`) for specialized latency work.
6. **Match `CONFIG_HZ`/preemption to role.** Server distributions default to 250 Hz voluntary preemption, which favors throughput; note that at 250 Hz a 0.75 ms base slice isn't enforced between ticks without hrtimer preemption, so slice-level latency guarantees are softer than the knob implies.

## Caveats

- **"CFS" is now a misnomer for the code.** `fair_sched_class` still carries the CFS name, but since 6.6 the pick logic is EEVDF (`pick_eevdf()`); the `vruntime`/weight/PELT machinery is shared, so most CFS-era intuition about weights and fairness still holds. Statements about `sched_latency_ns`/`sched_wakeup_granularity_ns` apply to pre-6.6 kernels; 6.6+ uses `base_slice_ns`.
- **Tunable defaults are CPU-scaled and distro-patched.** The 6 ms latency and 0.75 ms granularity/base-slice are *base* values scaled by `(1 + ilog(ncpus))` under the default `SCHED_TUNABLESCALING_LOG`; actual runtime values vary by core count, and distributions (e.g., zen/CachyOS) ship different numbers. Verify on your system via `/sys/kernel/debug/sched/`.
- **The per-task latency figures are idealized.** The `nr_running × base_slice` model assumes equal-weight, always-runnable, single-core tasks and ignores load balancing across cores, wakeup preemption, RUN_TO_PARITY batching, and cgroup hierarchy. Real latencies differ; treat them as order-of-magnitude.
- **The PostgreSQL per-core numbers combine scheduler math with database-internal effects.** The linear-latency scenarios are scheduler lower bounds; real degradation is worse and workload-dependent because of LWLock contention, `GetSnapshotData()` scaling, cache effects, and I/O. The `(cores×2)+spindles` formula is a validated *starting point*, not a law — the PostgreSQL wiki itself stresses testing, and the "34%" and "2×" figures are specific to their test rigs (Aurora db.r7g.4xlarge, and a 20-core PG12 box respectively).
- **EEVDF is still evolving.** Feature flags and defaults (RUN_TO_PARITY, DELAY_DEQUEUE, PREEMPT_SHORT) have changed between 6.6 and 2025/2026 kernels and continue to be tuned; some third-party trees (e.g., BORE on CachyOS) flip these defaults. Confirm against the exact kernel version in use.
